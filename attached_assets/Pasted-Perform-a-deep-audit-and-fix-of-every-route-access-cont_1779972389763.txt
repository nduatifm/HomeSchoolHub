Perform a deep audit and fix of every route, access control, and authentication flow across the entire LyraPrep application. Users with correct credentials are being blocked from accessing pages and features they should have access to. The root cause may be in route guards, role checks, session handling, database queries, or any combination. Do not add new features. Do not refactor working code. Find every point of failure and fix it. Work through each section completely before moving to the next.

Section 1 — Session and authentication layer
This is the foundation. A broken session causes cascading failures everywhere else, so fix this section before touching anything else.

Verify that after a successful login, the session correctly stores and exposes the user's id, role, and any other fields that downstream route guards depend on
Confirm the session persists correctly across page navigations and does not silently expire or reset mid-session
Verify that a hard refresh on any page does not log the user out or lose their session state
Check that the session correctly identifies the role as exactly teacher, parent, or student — no casing inconsistencies (Teacher vs teacher), no null values, no undefined role fields
Confirm that after logout the session is fully cleared — no stale role, user ID, or token data remains in memory, cookies, or local storage
Check that if a session expires while the user is active, they are redirected to login with a clear message rather than seeing a broken or empty page
Log the raw session object on every protected route during this audit and confirm it always contains the expected shape before the route renders


Section 2 — Route guards and role enforcement

Audit every protected route in the application and list which roles are permitted to access it
Verify that each route guard reads the role from the session correctly — not from a prop, not from a URL param, not from local state that could be stale
Confirm that a Teacher session cannot access Student-only or Parent-only routes and receives a clear redirect or error — not a blank page or silent failure
Confirm the same cross-role isolation for Student and Parent sessions
Check for any route that is accidentally unguarded — accessible without a valid session or accessible to the wrong role
Check for any route guard that is too strict — blocking a valid role from a page they should have access to
Verify that route guards do not flash protected content before redirecting an unauthorized user — the check must happen before render
Confirm that direct URL access (typing a route into the browser) enforces the same guards as in-app navigation — not just client-side guards that can be bypassed
Check that query parameters and route params (e.g. classroomId, studentId, assignmentId) are validated server-side and cannot be manipulated to access another user's data


Section 3 — Teacher access audit
Walk through every Teacher-facing route and feature and confirm it loads correctly with a Teacher session:

Sidebar nav items: Assignments, Grade Submissions, Study Materials, Students, Feedback, Messages, Classrooms — each must route to the correct page without error
Classrooms: Teacher can view their list of grade folders, open a grade folder, open a subject subfolder, and access all four tabs (Assignments, Study Materials, Feed, Grades) without error
Assignments: Teacher can create a new assignment (including the required Type field), view the assignments list, open an assignment detail, and access Grade Submissions for that assignment
Grade Submissions: Teacher can view all student submissions for an assignment, open an individual submission, enter a grade, and return a submission for revision with a required note
Study Materials: Teacher can create, view, and open a study material inside a subject subfolder
Students: Teacher can view their student roster and open an individual student profile
Grading Policy: Teacher can open the Grading Policy settings panel inside a subject, enter weights, and save a valid policy
Messages: Teacher can view their thread list, open a student thread, read the full three-way message history, and send a message
Feedback: Teacher can access the Feedback page without error

For each item above: if the page loads but data does not appear, trace the API call, log the raw response, and identify whether the issue is a failed query, a permission error, a broken join, or a frontend rendering bug. Fix every failure found.

Section 4 — Student access audit
Walk through every Student-facing route and feature and confirm it loads correctly with a Student session:

Sidebar nav items: Assignments, Study Materials, Feedback, Messages, My Classes — each must route to the correct page without error
My Classes: Student sees only the grade folders and subject subfolders they are enrolled in — not all classrooms. Clicking a grade folder expands it. Clicking a subject subfolder opens the workspace
Inside a subject subfolder: Student can access the Assignments tab, Study Materials tab, Feed tab, and Grades tab without error
Assignments: Student can view their assigned work, open an assignment, complete it, and submit it without error. If an assignment has been returned for revision, the teacher's note appears at the top in amber and the assignment is unlocked for editing and resubmission
Study Materials: Student can open and view materials shared in their enrolled subjects
Grades: Student sees their weighted overall grade and per-type breakdown. Pending types show in amber. The "Based on graded items only" note appears when applicable
Messages: Student sees the thread with their teacher and parent messages in the same chronological thread. Student can send a message. The thread does not error or show blank when there are no messages yet
Feedback: Student can access the Feedback page without error

For each item: trace any failure from the session through the API to the database query and fix the root cause — not just the symptom.

Section 5 — Parent access audit
Walk through every Parent-facing route and feature and confirm it loads correctly for both Owner and Member roles:

Sidebar nav items: My Children, Find a Tutor, Invite Student, Progress Reports, Messages, Classes — each must route to the correct page without error
My Children: Parent sees their child cards. Owner sees the Team panel with member avatars, role badges, and pending invites. Member sees the shared child card with "Member" badge and "Shared by [Owner name]" sub-label
Classes: Parent sees classrooms filtered to their child's enrollments only — not all classrooms in the system
Inside a subject subfolder: Parent can access the Assignments tab, Study Materials tab, Feed tab, and Grades tab in read-only mode without error
Grades: Parent sees the same weighted grade breakdown as the student — overall percentage, per-type breakdown, pending types in amber
Messages: Owner sees the full thread and can send messages. Member sees the full thread but the composer is hidden. Neither role sees other children's threads
Progress Reports: Parent can access Progress Reports without error
Team management (Owner only): Owner can invite a new member, cancel or resend a pending invite, change a member's role, and remove a member. The last-Owner guard blocks demotion or removal when only one Owner remains
Confirm that a Member session cannot access Owner-only actions — the UI hides them and the API rejects them


Section 6 — Database and API layer

For every route that returns empty data for a valid user, trace the database query and confirm the joins, filters, and foreign keys are correct
Verify that enrollment queries for students correctly filter classrooms, assignments, and materials to only what that student is enrolled in — not all records in the table
Verify that parent queries filter to their child's data only — not all students in the system
Check for any query that returns null or undefined silently instead of an empty array — these cause frontend rendering crashes that look like access errors to the user
Confirm that all API endpoints validate the requesting user's identity and role server-side — not just on the client. A user should not be able to call an endpoint directly with a manipulated role or ID and receive data they are not permitted to see
Check for any N+1 query patterns or missing database indexes on frequently joined columns (child_id, parent_id, student_id, classroom_id) that could cause slow or failed data loads that appear as access errors


Section 7 — Frontend rendering and error masking

Audit every page for error boundaries, loading states, and empty states that may be silently swallowing real errors and showing a blank or frozen page instead
Confirm that when an API call fails, the error is surfaced to the user via the unified in-app notification system — not swallowed silently or logged only to the console
Check for any component that renders conditionally based on a role or permission check and confirm the condition logic is correct — particularly any isTeacher, isOwner, canEdit boolean flags derived from the session
Verify that no page renders a blank white screen for a valid user — every page must have a defined loading state, error state, and empty state
Check for any hardcoded user IDs, role strings, or classroom IDs left in the codebase from development or testing that could cause the wrong data to load for real users


Section 8 — Cross-cutting reliability checks

Confirm that every form submit button shows a loading state while the request is in flight and does not allow double submission
Verify that no browser-native alert(), confirm(), or beforeunload dialogs appear anywhere — all messages must use the unified in-app notification system from the top center of the screen
Confirm that back navigation on every drill-down page returns the user to the correct previous page — not a hardcoded fallback route
Check that unsaved changes on any editable page trigger the in-app warning dialog — not a browser pop-up
Verify that the application does not throw unhandled promise rejections anywhere — wrap all async calls in try/catch with proper error handling


Section 9 — Post-fix smoke test
After all fixes are applied, run through this checklist for each role before marking the task complete:

Log in as a Teacher → navigate every sidebar item → confirm all pages load with correct data
Log in as a Student → navigate every sidebar item → open a classroom → view assignments, materials, and grades → send a message
Log in as a Parent Owner → navigate every sidebar item → open a classroom → view grades → send a message → manage the team panel
Log in as a Parent Member → confirm read-only access to all pages → confirm composer is hidden → confirm team management is hidden
Attempt to access a Teacher route from a Student session and confirm the redirect or error is correct
Attempt to access a Parent Owner action from a Member session and confirm the API rejects it
Hard refresh on every role's dashboard and confirm the session and data persist correctly
