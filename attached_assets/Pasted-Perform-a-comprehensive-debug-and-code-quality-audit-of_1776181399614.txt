Perform a comprehensive debug and code quality audit of the entire LyraPrep codebase. Do not add new features. The goal is to find and fix existing bugs, close logical gaps, and handle edge cases that are currently unhandled. Work through each layer systematically.
1. Database and schema
Review shared/schema.ts and all Drizzle migration files.

Check for missing onDelete cascade or set null rules on foreign keys — any FK without an explicit delete rule is a silent data integrity risk. Example: if a student is removed, what happens to their formSubmissions, formAnswers, classroomSubmissions, studentAssignments?
Check for columns that are nullable in the schema but treated as non-null in application code, or vice versa.
Check for missing unique constraints that the application logic assumes exist (e.g. one form per assignment, one submission per student per form).
Check for indexes on columns that are frequently queried but not indexed (e.g. studentId, classroomId, assignmentId on join tables).
Verify that all new tables added for the form builder (assignmentForms, formQuestions, formSubmissions, formAnswers) have been migrated and that relations are registered in the Drizzle schema.

2. API route gaps and logic errors
Audit every Express route in the server.

Authorization gaps: every route that modifies data should verify the requesting user owns or has permission over the resource. Check specifically: can a student call teacher-only routes by guessing the endpoint? Can a teacher from classroom A modify data in classroom B? Can a parent access another parent's child's data?
Missing validation: check for routes that accept user-supplied JSON or FormData without validating required fields, types, or length limits. A missing title or negative points value should return a 400, not crash the server or insert bad data.
Transaction gaps: any operation that writes to multiple tables should use a database transaction. Check specifically: form submission (inserts formSubmissions + multiple formAnswers + upserts classroomSubmissions) — if any insert fails mid-way, the others should roll back. Assignment creation with a form schema should be atomic.
Race conditions: the unique constraint on (formId, studentId) in formSubmissions should be enforced at the DB level, and the API should handle the unique violation error gracefully (return 409, not 500).
Missing 404 handling: routes that look up a resource by slug or ID should return a proper 404 if not found, not crash or return undefined.
File upload edge cases: check the /with-file endpoints — what happens if the file upload to Cloudinary fails mid-request? Is the DB record still written? It shouldn't be. The Cloudinary upload should complete before any DB writes.
Check all PATCH routes: do they correctly do partial updates (only update provided fields) or do they accidentally overwrite missing fields with null?

3. Frontend query and mutation gaps
Audit all useQuery and useMutation calls across components.

Check for queries that run without their dependencies being ready — e.g. enabled: !!studentId where studentId could be 0 (falsy) for a valid student. 0 evaluates to false, so queries may never fire for the first student in the DB.
Check that all mutations call queryClient.invalidateQueries on the correct query keys after success. A stale cache after create/update/delete is a common source of "I saved it but the UI didn't update" bugs.
Check error handling: mutations that fail should show a toast with a meaningful message. Verify no mutation has an empty onError or swallows errors silently.
Check that loading and error states are handled in every useQuery — a component that renders data.map(...) without checking isLoading will crash on first render.
Check useQueries (plural) results — the results array is index-matched to the queries array, and if the queries array length changes between renders it can cause index mismatches. Verify all useQueries usages are stable.

4. Form builder and renderer
Audit FormBuilder.tsx, FormRenderer.tsx, and FormResponses.tsx.

FormBuilder: can a teacher save a form with zero questions? Can they save a multiple choice question with zero options? Both should be prevented with validation before the save mutation fires.
FormBuilder: the id field on each FormQuestion uses Math.random().toString(36).slice(2, 10) — this is not guaranteed to be unique. Replace with crypto.randomUUID() which is available in all modern browsers.
FormRenderer: required field validation on submit should highlight the specific question that failed, not just block submission silently. Check that the validation error state is cleared when the student starts typing.
FormRenderer: what happens if a student navigates away mid-form and comes back? Their in-progress answers are lost. Consider persisting draft answers to localStorage keyed by formId and restoring them on mount, clearing on successful submit.
FormRenderer: the already-submitted read-only state should be fetched from the server (GET /api/forms/:formId/my-submission), not just shown based on local mutation success. If the student submitted in a different tab or session, the current session won't know.
FormResponses: if a student submitted but didn't answer a particular question (e.g. it was optional), the response display should handle a missing answer gracefully rather than crashing or showing undefined.

5. Authentication and session handling

Check that the session token is validated server-side on every protected route, not just checked for presence. An expired or forged token should return 401.
Check that the useAuth context handles the case where the session token exists in localStorage but the server returns 401 — the client should clear the token and redirect to login, not loop.
Check role-based guards on the frontend: pages that are teacher-only (NewAssignmentPage, FormBuilder, etc.) redirect non-teachers, but is there a flash of the page content before the redirect fires? Add a loading state that prevents rendering until the user role is confirmed.

6. File and attachment handling

Check the maximum file size enforcement: is it enforced on the server as well as the client? A user can bypass the client-side 10 MB check by calling the API directly.
Check MIME type validation: accept="image/*,.pdf,.doc,.docx,.txt" on file inputs is advisory only. The server should verify the actual MIME type or file extension of uploaded files.
Check what happens when a Cloudinary URL is stored but Cloudinary later returns a 404 for that asset (deleted externally). Students clicking "Open PDF" would get a broken link. Consider storing the Cloudinary public ID separately so assets can be re-fetched or replaced.

7. Real-time and stale data

The classroom feed (FeedTab) uses useQuery with no refetchInterval. If a teacher posts an announcement while a student is on the page, the student won't see it until they refresh. Add refetchInterval: 30000 (30 seconds) to the feed query.
conversationSummaries in StudentDashboard uses staleTime: 30000 — this means message previews can be up to 30 seconds stale. Verify this is acceptable or reduce it.
The MessageThread component should handle the case where the conversation partner has been unassigned (teacher removed from student) — the thread should show a graceful "no longer connected" state rather than an empty thread.

8. UI edge cases

Long text: test all truncated text (truncate, line-clamp-*) with very long assignment titles, classroom names, and student names. Some components may overflow or clip awkwardly.
Empty classrooms: a classroom with no enrolled students, no assignments, and no classwork should show proper empty states in each tab, not crash.
Archived classroom: verify that the isArchived flag is respected everywhere — teachers should not be able to create assignments, posts, or classwork in archived classrooms. Check that all mutation buttons are disabled when isArchived === true.
Zero points: what happens if a teacher sets points to 0? The gradebook percentage calculation would divide by zero. Add a guard: totalPoints > 0 ? Math.round((earned / totalPoints) * 100) : 0.
Student with no submissions: the grade summary row for a student with no submissions should show 0 / totalPoints (0%) not crash or show NaN%.
Date formatting: the formatDueDate function uses new Date(dateStr + "T00:00:00") to avoid timezone shifts — verify this pattern is applied consistently everywhere dates are parsed from strings. Any new Date(dateStr) without the time suffix will parse as UTC midnight and display the wrong day in non-UTC timezones.

9. Navigation and routing

The safeNavigate function in NewAssignmentPage uses window.confirm which is blocked in some iframe contexts and looks inconsistent with the app's design. Replace with a proper in-app confirmation dialog using the existing Dialog component.
Check all useRoute / useLocation usages — are there any routes that could match ambiguously? E.g. /classrooms/:slug/materials/new and /classrooms/:slug/materials/:materialSlug — does new get matched as a materialSlug? Add a guard in the route handler to treat "new" as a reserved slug.
Check that navigating back with the browser back button from a form creation page doesn't leave orphaned data if the form was partially saved.

10. Accessibility and keyboard navigation

All <button> elements that use onClick should have accessible labels. Check for icon-only buttons missing aria-label or title attributes — screen readers will announce these as blank buttons.
The FormBuilder question list should support keyboard navigation — arrow keys to move between questions, Delete to remove the active question.
The FormRenderer option rows (multiple choice, checkbox) are styled <button> elements — verify they respond to Space and Enter keys as expected.
Check that all modals and dialogs trap focus correctly — tabbing should not escape an open dialog.

For each issue found: state the file and line number, describe the bug or gap, and apply the fix directly. Group fixes by category. After all fixes are applied, run a final check to confirm no TypeScript errors remain and no console.error calls are triggered on page load.
